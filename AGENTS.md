# 1. Цель продукта

Нужно создать рабочий веб-прототип бонусной crash-игры "Воздушный шар".

Игрок ставит бонусные баллы, наблюдает за полетом шара и ростом коэффициента, а затем решает: забрать выигрыш сейчас или рискнуть ради большего. Если шар лопается до успешного cashout, ставка сгорает.

Продукт должен не просто "сжигать" бонусные баллы, а мотивировать игрока:

- делать повторные ставки;
- оставаться в игре дольше;
- возвращаться за прогрессом, наградами и рейтингом;
- ощущать понятный риск/выгоду;
- видеть эффект упущенной выгоды после cashout.

Ключевой цикл:

```text
выбор версии шара
-> выбор ставки и бустера
-> списание бонусов
-> полет шара
-> рост коэффициента
-> cashout или crash
-> итог, очки, награда
-> история
-> повторная игра
```

Игровой цикл должен быть понятен без объяснений от команды.

# 2. Обязательный стек проекта

Постановка допускает разные frontend-технологии, но в этом репозитории выбран и обязателен следующий стек.

## Backend

Основные игровые механики backend должны быть реализованы на Java.

Подходящие варианты:

- Spring Boot;
- Quarkus;
- Micronaut;
- Jakarta EE;
- Vert.x;
- другой Java-фреймворк, если он уже используется или лучше подходит архитектуре.

Не менять Java для основных игровых механик. Для второстепенных вспомогательных задач допустимы другие языки только при явной пользе и без выноса авторитетной игровой логики из Java backend.

## Frontend

Frontend должен использовать:

- React;
- TypeScript;
- Tailwind CSS.

Для графики и анимаций можно использовать Canvas, WebGL, Three.js, React Three Fiber, PixiJS, Framer Motion, GSAP или CSS-анимации, если это улучшает игровой опыт. Не добавлять тяжелый графический стек без необходимости.

# 3. Приоритет требований

Постановка делит функциональность на обязательный минимум и дополнительные возможности.

## Обязательный минимум для проверки

Решение должно позволять экспертам пройти сценарии 1-5 без обращения к команде:

1. выбор ставки и запуск игры;
2. успешный cashout и результат раунда;
3. проигрыш через crash;
4. активация бустера;
5. управление параметрами без изменения исходного кода.

Эти сценарии нельзя удалять, подменять моками или реализовывать только на frontend.

## Дополнительные возможности

Следующие функции повышают оценку и желательны, но по постановке не являются обязательной демонстрацией базового решения:

- отдельный стартовый экран выбора темы;
- живой рейтинг;
- турнирная таблица;
- апсейл-попап "Закрепи успех";
- полноценная административная панель вместо конфигурационного файла;
- мгновенный повтор с той же ставкой;
- восстановление незавершенной игры;
- продвинутая анимация и звук.

Если время ограничено, сначала довести до стабильности обязательные сценарии 1-5, затем добавлять расширения.

# 4. Архитектура

Предпочтительна простая архитектура с ясными доменными границами.

Микросервисный подход допустим, но не обязателен. Не создавать микросервисы ради микросервисов. Для MVP нормально реализовать модульный монолит, если домены остаются разделенными.

Домены, которые должны быть отделены хотя бы на уровне пакетов/модулей:

- game: раунды, состояния, crash, cashout, уровни;
- balance/user: пользователь и бонусный баланс;
- boosters: правила и активация бустеров;
- rewards: дополнительные игровые награды;
- scoring: игровые/турнирные очки;
- history: история завершенных раундов;
- config/admin: конфигурация и управление параметрами;
- leaderboard: рейтинг, если реализован;
- offers: персонализированные предложения, если реализованы.

Предпочитать ясные границы доменов и простое развертывание вместо множества мелких сервисов и лишней инфраструктуры.

# 5. Авторитетность backend

Backend является источником истины для всех значимых игровых операций.

Frontend не должен определять:

- точку crash;
- позицию бустера;
- финальный коэффициент;
- успешность cashout;
- сумму выигрыша;
- начисление очков;
- выдачу наград;
- изменения баланса.

Вся математика расчета точки crash, позиции бустера, начисления очков и выигрыша выполняется на сервере.

Backend должен валидировать:

- пользователя;
- доступный бонусный баланс;
- ставку;
- выбранный режим;
- право на бустер;
- состояние текущего раунда;
- допустимость cashout;
- идемпотентность повторных запросов;
- начисление выплат, очков и наград.

Не размещать чувствительную игровую логику в frontend.

# 6. Режимы игры

Должны поддерживаться две версии игры.

## Красный шар

- 12 уровней;
- более рискованное ощущение;
- более высокий потенциальный выигрыш;
- более напряженная и интенсивная визуальная подача.

## Зеленый шар

- 9 уровней;
- более стабильное ощущение;
- спокойнее визуально;
- ниже воспринимаемый риск.

Шар является обязательной темой продукта. Не заменять его ракетой, машиной, самолетом, абстрактным прогресс-баром или другим объектом.

Отдельный экран выбора темы желателен и оценивается как расширение. Если отдельного стартового экрана нет, пользователь должен иметь возможность переключить красную/зеленую версию на экране выбора ставки.

# 7. Ставки и бонусный баланс

Базовые ставки MVP:

```text
50
150
300
600
```

Валюта ставки - бонусные баллы.

На экране выбора ставки игрок должен видеть:

- текущий бонусный баланс;
- стоимость выбранной ставки;
- какой бустер связан с выбранным вариантом;
- достаточно ли бонусов;
- что будет списано при старте.

Постановка описывает 4 фрагмента пазла как пример визуального решения. Можно использовать другой обоснованный паттерн, но четыре значения ставок и смысл бустера должны быть читаемы сразу.

Если баланса недостаточно:

- недоступная ставка должна быть явно обозначена;
- запуск раунда должен быть невозможен;
- пользователь должен получить понятную обратную связь, например "Не хватает бонусов";
- можно открыть сценарий пополнения/апсейла, но реальные платежи запрещены.

Ставка списывается при старте раунда после серверной проверки. Повторный запрос старта не должен списывать ставку дважды.

---

# 8. Бустеры

Бустеры обязательны для базового сценария.

Игрок выбирает ставку без усиления или с бустером. В постановке фрагменты ставки связаны с множителями:

```text
x1
x2
x3
x4
```

Если выбран бустер выше x1:

- позиция бустера на уровне рассчитывается backend до начала раунда;
- вероятность позиции на уровнях настраивается отдельно для красной и зеленой версии;
- frontend только отображает полученную от сервера позицию/состояние;
- бустер активируется, только если шар достиг его уровня до cashout;
- после cashout бустер уже не активируется;
- при активации текущий коэффициент умножается на значение бустера;
- начисляются дополнительные очки;
- игрок видит понятный визуальный эффект.

Правила бустеров должны быть конфигурируемыми.

---

# 9. Crash и cashout

Точка crash определяется backend до начала полета или в рамках авторитетной серверной инициализации раунда.

Кнопка "Забрать" видна с начала раунда, но недоступна до прохождения первого уровня.

После первого уровня игрок может запросить cashout. Cashout считается успешным только после подтверждения backend.

При успешном cashout:

- фиксируется коэффициент cashout;
- выигрыш рассчитывается как `ставка x зафиксированный коэффициент x примененные бустеры`;
- выплата зачисляется на баланс один раз;
- интерфейс ясно показывает, что выигрыш уже зафиксирован;
- шар продолжает визуальный полет до исходной точки crash;
- сумма выигрыша больше не меняется;
- после crash открывается итоговый экран;
- желательно показать сообщение вроде "Могли бы забрать больше".

Если crash наступил до успешного cashout:

- ставка сгорает;
- шар визуально лопается/сдувается;
- игрок видит проигрыш, коэффициент crash, очки и награду по правилам;
- результат сохраняется в истории.

Cashout должен быть идемпотентным. Двойной клик, retry или повтор события не должны приводить к двойной выплате.

---

# 10. Уровни, коэффициент и очки

Шар поднимается вертикально, проходит уровни, коэффициент растет в режиме, близком к реальному времени.

Игрок всегда должен понимать:

- текущий уровень;
- пройденные уровни;
- следующий уровень;
- текущий коэффициент;
- потенциальный выигрыш;
- ставку;
- состояние бустера;
- доступен ли cashout;
- состояние раунда.

За прохождение уровней начисляются игровые очки. Количество очков за уровень должно быть параметром конфигурации, например `points_per_line`.

Очки являются отдельной сущностью от бонусных баллов и выигрыша. Их роль должна быть объяснена в правилах и документации.

---

# 11. Итоговый экран, награды и повтор

Итоговый экран показывается после завершения полета, то есть после crash. Если игрок сделал cashout раньше, итоговый экран все равно открывается только после того, как шар долетел до crash.

Экран результата должен показывать:

- выигрыш или проигрыш;
- ставку;
- коэффициент crash;
- коэффициент cashout, если был cashout;
- выплату или потерю ставки;
- заработанные игровые очки;
- дополнительную игровую награду;
- использованный/неактивированный бустер;
- действие "Играть снова".

Дополнительная игровая награда по итогам раунда обязательна. Это может быть фрагмент пазла, коллекционный предмет, новый бустер, временный множитель, бонусные баллы или другой элемент прогресса. Награда не должна быть только декоративной и должна быть описана в правилах.

Кнопка "Играть снова" возвращает к выбору ставки с сохранением выбранной темы.

Желательно добавить "Повторить с той же ставкой" как расширение.

Если игрок бездействует 10 секунд на экране результата, должен произойти переход на экран выбора темы, а если отдельного стартового экрана нет - на экран выбора ставки.

---

# 12. История раундов

История завершенных игр обязательна на экране выбора ставки.

История должна пополняться после завершения раундов и не зависеть от реализации рейтинга или турниров.

Минимальные поля истории:

- время;
- режим: красный или зеленый;
- ставка;
- результат: win/loss;
- коэффициент crash;
- коэффициент cashout, если был;
- выплата;
- заработанные очки;
- бустер;
- награда.

Backend должен быть источником истины для истории.

# 13. Правила игры

До подтверждения ставки должен быть отдельный доступ к правилам.

Правила должны соответствовать фактически реализованной механике и объяснять:

- выбор ставки;
- когда списываются бонусы;
- рост коэффициента;
- уровни;
- действие бустера;
- условия cashout;
- условия выигрыша;
- условия потери ставки;
- начисление очков;
- получение наград;
- различия красной и зеленой версии;
- как меняются параметры игры, если это важно для пользователя.

Критические правила не должны существовать только в онбординге или анимации.

# 14. Конфигурация и управление параметрами

Управление ключевыми параметрами без изменения исходного кода обязательно.

Минимально допустимый вариант: конфигурационный JSON/YAML-файл с понятной структурой и применением настроек без правки кода. Предпочтительный вариант: административный UI.

Нужно уметь настраивать, где применимо:

- активность игры;
- доступные ставки;
- параметры красной и зеленой версии;
- количество уровней;
- множители уровней;
- распределение crash;
- ограничения коэффициента;
- темп роста коэффициента;
- FPS/шаг симуляции, если это часть модели;
- вероятность позиции бустера по уровням;
- значения множителей бустеров;
- очки за уровень;
- бонусные очки за cashout;
- бонусные очки за бустер;
- правила дополнительных наград;
- правила апсейла, если реализован;
- параметры турнира/рейтинга, если реализованы.

Для обязательной проверки эксперт должен иметь возможность изменить количество очков за прохождение уровня и в новом раунде увидеть новое начисление. Исходный код при этом не редактируется.

Конфигурация должна быть описана в README или отдельной документации: назначение параметров, допустимые значения, порядок применения.

# 15. Real-time и события

Передача текущего коэффициента от сервера к клиенту должна быть близкой к реальному времени.

Допустимые варианты:

- WebSocket;
- Server-Sent Events;
- polling с интервалом не более 1 секунды.

Не внедрять сложную real-time-инфраструктуру без необходимости.

Полезные типы событий:

```text
ROUND_STARTED
LEVEL_REACHED
MULTIPLIER_UPDATED
BOOSTER_ACTIVATED
CASHOUT_CONFIRMED
CRASH
ROUND_FINISHED
REWARD_GRANTED
LEADERBOARD_UPDATED
```

Не раскрывать клиенту внутренние данные случайной генерации, позволяющие предсказать исход раунда.

# 16. Дополнительные модули

## Живой рейтинг

Дополнительный сценарий. Если реализован:

- отображается во время игры;
- текущий игрок выделен;
- очки обновляются без перезагрузки;
- допустим polling около 1 секунды;
- при изменении позиции есть понятная подсветка;
- элементы не должны перекрывать игровой интерфейс.

## Турнирная таблица

Дополнительный сценарий. Если реализована:

- открывается с экрана выбора ставки;
- показывает топ-3;
- показывает текущего игрока;
- при активном турнире показывает таймер;
- деперсонализация имен желательна, но для MVP допустимы никнеймы или полные имена.

## Апсейл "Закрепи успех"

Дополнительный сценарий. Если реализован:

- появляется после успешного cashout при выполнении условий;
- не показывается чаще одного раза за сессию;
- предлагает имитационную покупку/получение лотерейных билетов или бонусов;
- не подключает реальные платежи;
- закрывается автоматически по настраиваемому timeout.

# 17. Визуальный стиль и UX

Интерфейс должен быть выразительным, энергичным, игровым и понятным.

Можно вдохновляться атмосферой современных лотерейных/казино-продуктов, но нельзя копировать:

- логотипы;
- фирменный стиль;
- защищенные изображения;
- точные UI-макеты;
- proprietary-графику;
- отличительные элементы сторонних брендов.

Обязательные визуальные принципы:

- воздушный шар - главный визуальный объект;
- красная и зеленая версии различимы;
- уровни читаются как вертикальный прогресс;
- коэффициент крупный и заметный;
- ставка, баланс, потенциальный выигрыш и cashout всегда понятны;
- эффекты не перекрывают важные действия и значения;
- результат раунда невозможно перепутать.

Для красной версии использовать более напряженную, рискованную и интенсивную подачу. Для зеленой - более спокойную и стабильную. Обе версии должны выглядеть частью одной игры.

Звук опционален, но если используется, игрок должен иметь возможность его отключить.

---

# 18. Адаптивность и производительность

Решение должно быть адаптивным веб-приложением.

Поддерживаемый диапазон ширины:

```text
320 px - 1920 px
```

Все ключевые элементы должны оставаться читаемыми и доступными для нажатия на мобильных и десктопных размерах.

Desktop важен, но мобильный сценарий по постановке тоже должен быть пригодным. Не строить frontend так, чтобы мобильная версия требовала переписывания.

Анимация полета шара, изменения коэффициента и пересечения уровней должна быть плавной. Ориентир - до 60 FPS на средних мобильных устройствах, если выбранная графическая технология позволяет.

Проверять Chrome, Safari и Firefox. Не использовать экспериментальные браузерные возможности без fallback или явного описания ограничения.

---

# 19. Честность, проверяемость и seed

Результат игры должен быть невозможно подделать со стороны клиента.

Рекомендуется реализовать упрощенную "provably fair" схему:

- backend до начала раунда рассчитывает исход;
- клиент получает хеш результата/seed;
- после завершения раунда можно показать данные для проверки;
- алгоритм описан в документации.

Полная криптографическая верификация не обязательна, но хеш и понятное описание повышают доверие и оценку.

Желательно предусмотреть developer/test-режим с фиксированным seed для воспроизводимости раундов при тестировании и демонстрации.

---

# 20. Идемпотентность и состояние раунда

Раунд должен иметь явную state machine, например:

```text
CREATED
BET_PLACED
RUNNING
CASHED_OUT
CRASHED
FINISHED
```

Имена могут отличаться, но переходы должны валидироваться backend.

Недопустимые переходы, например `FINISHED -> CASHED_OUT`, должны отклоняться.

Система должна корректно обрабатывать:

- повторный старт раунда;
- двойной cashout;
- сетевые retry;
- обновление страницы;
- временную потерю соединения;
- дубли frontend-событий.

Нельзя допустить повторного списания ставки, повторной выплаты или повторной выдачи награды.

Полное восстановление незавершенной игры на 30 дней не обязательно. Упрощенное восстановление через localStorage на короткое время допустимо как дополнительное преимущество, но не заменяет серверную авторитетность.

---

# 21. Реальные платежи и лотереи

Реальные платежные и лотерейные интеграции не требуются и не должны подключаться без явного требования.

Допустима только имитация:

- покупки;
- пополнения;
- получения бонусов;
- покупки условных лотерейных билетов;
- активации персонального предложения.

Не использовать реальные платежные credentials. Не связывать игровое ядро жестко с фейковой лотерейной интеграцией.

---

# 22. Документация

В репозитории должен быть README.md или отдельные документы, позволяющие экспертам проверить решение без обращения к команде.

Документация должна содержать:

- стек технологий;
- команды запуска;
- зависимости;
- демонстрационный пользователь с ненулевым балансом или сценарий пополнения;
- структуру проекта;
- описание архитектуры и модели данных;
- описание API или Swagger/OpenAPI, если есть;
- выбранную математическую модель;
- логику генерации crash и позиции бустера;
- расчет выигрыша, очков и наград;
- параметры конфигурации и допустимые значения;
- порядок применения настроек;
- перечень реализованных функций;
- известные ограничения;
- способ пройти обязательные сценарии 1-5.

Health-check полезен, но не заменяет проверяемость игровых операций.

---

# 23. Тестирование

Core-механики требуют автоматических тестов, прежде всего на backend.

Минимально тестировать:

- создание раунда;
- списание ставки;
- недостаточный баланс;
- генерацию crash на backend;
- позицию бустера на backend;
- рост коэффициента/уровни;
- успешный cashout;
- crash до cashout;
- double-click/retry cashout;
- cashout после crash;
- активацию бустера;
- отсутствие активации бустера после cashout;
- расчет выплаты;
- расчет очков;
- выдачу награды;
- сохранение истории;
- применение измененной конфигурации;
- недопустимые переходы state machine.

Frontend-тесты должны покрывать ключевые видимые состояния: недоступная ставка, доступность cashout после первого уровня, результат выигрыша/проигрыша, правила, история.

Не отключать тесты ради зеленого билда. Не заявлять, что тесты прошли, если они не запускались.

---

# 24. Definition of Done

Базовый MVP нельзя считать готовым, если отсутствует хотя бы один обязательный сценарий 1-5.

Минимальная готовность:

- Java backend для основных игровых механик;
- React + TypeScript + Tailwind frontend;
- красная и зеленая версии;
- 12 уровней для красной, 9 для зеленой;
- четыре ставки 50/150/300/600;
- бонусный баланс;
- проверка недостаточного баланса;
- серверное списание ставки;
- серверная генерация crash;
- серверная позиция бустера;
- рост коэффициента;
- cashout после первого уровня;
- проигрыш через crash;
- post-cashout полет до crash;
- бустеры;
- игровые очки;
- дополнительная награда;
- история раундов;
- правила до старта;
- итоговый экран;
- "Играть снова";
- управление параметрами без изменения кода;
- документация для самостоятельной проверки.

Расширенная готовность:

- отдельный экран выбора темы;
- живой рейтинг;
- турнирная таблица;
- апсейл;
- полноценная админка;
- мгновенный повтор;
- восстановление состояния;
- продвинутая анимация и звук;
- provably fair hash/seed.

---

# 25. Приоритет реализации

Если времени мало, работать в таком порядке:

1. server-authoritative игровые механики;
2. состояние раунда и идемпотентность;
3. ставки, баланс, недостаточный баланс;
4. красный/зеленый режим и уровни;
5. crash и cashout;
6. post-cashout полет до crash;
7. бустеры;
8. очки и дополнительная награда;
9. итоговый экран и история;
10. правила игры;
11. конфигурация без изменения кода;
12. документация и демонстрационный пользователь;
13. адаптивность 320-1920 px;
14. живой рейтинг и турнирная таблица;
15. апсейл;
16. полноценная админка;
17. advanced visuals/sound.

Не жертвовать корректностью server-authoritative механики ради визуальных эффектов.

---

# 26. Общие инженерные правила

Перед изменениями:

1. изучить существующую реализацию;
2. понять архитектуру;
3. переиспользовать существующие компоненты и утилиты;
4. следовать текущим naming conventions;
5. выбирать минимальное корректное изменение;
6. не ломать нерелевантное рабочее поведение.

Предпочитать:

- maintainable-решения;
- явные доменные границы;
- централизованную конфигурацию;
- серверную валидацию;
- явные состояния;
- переиспользуемые компоненты;
- простые реализации.

Избегать:

- клиент-авторитетной игровой логики;
- magic numbers в UI;
- дублирования расчетов;
- giant components/services;
- лишних абстракций;
- произвольных зависимостей;
- технологий ради моды;
- копирования стороннего брендинга.

---

# 27. Запрещено агентам

AI-агенты не должны:

- менять Java для core backend;
- менять React/TypeScript/Tailwind как основной frontend-стек проекта;
- переносить crash/cashout/выплаты на клиент;
- фейково заявлять backend-интеграцию, если есть только frontend-моки;
- удалять обязательные сценарии 1-5 ради упрощения;
- смешивать бонусные баллы, игровые очки и награды в одну сущность без объяснения;
- подключать реальные платежи;
- жестко вшивать параметры игры в компоненты;
- отключать тесты ради прохождения сборки;
- скрывать ошибки без причины;
- заявлять о пройденных тестах без запуска;
- коммитить секреты;
- копировать защищенные элементы "Столото" или других брендов.

---

# 28. Финальный принцип

Для каждого значимого решения спрашивать:

> Делает ли это игру понятной, азартной, server-authoritative, конфигурируемой, проверяемой и расширяемой без компромисса с основной механикой воздушного шара?

Если нет - выбрать другое решение.
